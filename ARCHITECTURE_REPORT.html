Sentinel QA Analytics Dashboard

Comprehensive Architecture Report

Overview

Sentinel QA Analytics Dashboard is a full-stack AI-powered analytics platform designed to help Quality Assurance teams visualize, analyze, and derive insights from test data. It combines traditional data analytics with natural language processing, role-aware context, and multi-source data ingestion.

Core Characteristics

  • Full-stack application: Next.js frontend + FastAPI backend
  • AI-powered natural language queries and chart generation
  • Multi-source data ingestion (Allure, files, databases, APIs)
  • JWT-based authentication with role and workspace scoping
  • Session-aware conversation memory and learning signals
  • Dark/light theme toggle with responsive design
  • Token usage tracking and cost visibility

Component Interactions

The system follows a clean layered architecture with clear boundaries:

Application Layers

Presentation Layer (Next.js): Handles UI rendering, user interactions, session management, and API communication with caching.

API Layer (FastAPI): Provides RESTful endpoints with JWT authentication, request routing, and business logic coordination.

Processing Layer: Handles chat/chart logic, SQL generation, validation, and LLM orchestration.

Data Layer: Manages data loading, querying, memory storage, and ingestion orchestration.

Persistence Layer: Multi-database approach with SQLite (auth), LanceDB (vectors), and DuckDB (analytics).

Key Architectural Decisions

  1. Multi-database strategy: Different databases for different purposes (auth, vector search, analytics queries)
  2. LLM abstraction: LiteLLM enables provider flexibility without code changes
  3. Workspace scoping: Built-in multi-tenancy support at the auth and data layer
  4. Deterministic chart types: Chart type determined by regex, not LLM (prevents hallucination)
  5. Learning signals: Self-learning through chat history, keywords, and graph edges

Backend Request Flow

1. Authentication Flow

User ↓ POST /auth/login (username, password) ↓ [auth.py: authenticate_user] ├─ Load user from SQLite via UserStore ├─ Verify bcrypt hash └─ Generate JWT token (HS256, 24h expiry) ↓ Return token → localStorage (client) ↓ All subsequent requests: Authorization: Bearer {token}

Auth Details

  • Algorithm: HS256 (HMAC with SHA-256)
  • Token Duration: 24 hours
  • Storage: JWT payload includes username, role, workspace_id
  • Password Hashing: bcrypt with configurable rounds (default 12)
  • User Store: SQLite with SQLAlchemy ORM (free, no external dependency)

2. Chat Request Flow

User Input (Dashboard) ↓ POST /chat headers: Authorization, x-ingestion-id, x-role, x-project, x-session-id body: { message: "...", session_id: "..." } ↓ [handlers.handle_chat] ├─ Load ingestion context (DuckDB + LanceDB) ├─ Retrieve chat history (last 10 turns) ├─ Extract learning signals (keywords, patterns) ├─ Fetch related knowledge graph concepts ├─ Load role persona (CTO vs QA Engineer) └─ Load project context ↓ [llm_client.generate with CHAT_DECISION_PROMPT] ├─ LLM decides action: SQL query | vector search | direct answer └─ Returns JSON: { "action": "sql|vector|answer", "sql": "...", ... } ↓ [Execution based on action] ├─ IF sql: sanitize → validate → execute in DuckDB ├─ IF vector: search LanceDB for documents └─ IF answer: use context to generate response ↓ [llm_client.generate with CHAT_ANSWER_PROMPT] └─ Generate human-readable response ↓ [memory.store_chat] ├─ Save to LanceDB chat_history ├─ Extract keywords → update learning_signals └─ Update knowledge_graph_edges ↓ Return response → Client

3. Chart Generation Flow

User Input (Dashboard) ↓ POST /chart headers: Authorization, x-ingestion-id, x-role, x-project, x-session-id body: { message: "show me..." } ↓ [handlers.handle_chart] ├─ Detect chart type (deterministic via regex, NOT LLM) ├─ Load ingestion + role/project context ├─ Retrieve chart history └─ Build prompt with chart template constraints ↓ [llm_client.generate with CHART_SQL_PROMPT] └─ LLM generates SQL query (must be valid DuckDB) ↓ [data_loader.execute_sql] ├─ Sanitize SQL (remove markdown, comments) ├─ Validate against disallowed operations ├─ Execute in DuckDB └─ Return DataFrame ↓ [llm_client.generate with CHART_CODE_PROMPT] └─ LLM fills in Plotly template (pre-determined chart type) ↓ [Execute chart code] ├─ Render chart ├─ Apply visual layout (colors, fonts, margins) └─ Convert to JSON ↓ [memory.store_chart] ├─ Save to LanceDB chart_history └─ Update learning_signals ↓ Return chart JSON → Client (via Plotly.js)

🔑 Chart Type Safety Mechanism

Chart types are NOT decided by the LLM — they are detected deterministically using regex patterns. The LLM only fills in column names within a pre-written Plotly template. This prevents hallucination of unsupported chart types.

4. Data Ingestion Flow

User specifies source path ↓ [Frontend: POST /ingest/config2] body: { source_path: "/path/to/allure-results" } ↓ [Backend: main.py ingest_config2_endpoint] ├─ Infer source type (allure | file | db | api) ├─ Create config dict └─ Trigger UniversalIngester ↓ [UniversalIngester.ingest_source] ├─ Create ingestion folder: data/ingestion_TIMESTAMP/ ├─ Initialize LanceDB and DuckDB └─ Route to appropriate connector ↓ [Connector.fetch] └─ Fetch data based on type ↓ [Ingester._ingest_dataset] ├─ Flatten JSON columns ├─ Generate embeddings (sentence-transformers) ├─ Store in LanceDB └─ Register in DuckDB ↓ [Ingester.link_to_duckdb] └─ Build aggregate tables (module_metrics, project_metrics) ↓ [Ingester._generate_summary] ├─ Create summary.json with metadata ├─ Generate summary.md (formatted report) └─ Save to ingestion folder ↓ Ingestion complete → Cached in memory

5. SQL Query Safety

⚠️ Security: SQL Injection Prevention

All user-generated SQL is:

  • Sanitized (markdown removed, comments stripped)
  • Validated against disallowed keywords: DROP, DELETE, UPDATE, INSERT, ALTER, TRUNCATE, ATTACH, DETACH, COPY
  • Executed in read-only context (DuckDB session)
  • Limited to pre-loaded ingestion tables (no direct system access)

User Roles

  • cto — Executive/admin role; can view all user history, cross-workspace access
  • qa-engineer — Standard QA role; scoped to own sessions and data

LanceDB Tables (Per Ingestion)

LanceDB stores all ingested test data, documents, and learning artifacts. Key tables:

Data Tables

  • flattened_tests — One row per test result (after retry merge)
    • Columns: test_name, status, duration, error, spec_file, project_name, module_name, platform_type, browser
  • module_metrics — Aggregates by (project, module, platform)
    • Columns: total_tests, passed, failed, skipped, pass_rate, avg_duration
  • project_metrics — Aggregates by (project, platform)
    • Columns: module_count, total_tests, pass_rate, avg_duration
  • test_cases — Test metadata (backward-compat table)
    • Columns: module_name, priority, title (=test_name), project_name, platform_type

Memory & Learning Tables

  • chat_history — Chat messages and responses
    • Columns: id, workspace_id, user_id, ingestion_id, session_id, prompt, response, created_at
  • chart_history — Generated charts
    • Columns: id, workspace_id, user_id, ingestion_id, session_id, title, chart (Plotly JSON), created_at
  • learning_signals — Keyword patterns and frequency
    • Used to surface related concepts and accelerate future queries
  • knowledge_graph_edges — Co-occurrence graph of keywords
    • Enables semantic retrieval and context expansion

DuckDB Query Execution

[Load Ingestion] ├─ Create DuckDB in-memory connection ├─ Register LanceDB tables as views └─ Pre-compute aggregates ↓ [User SQL Query] ├─ Sanitize (remove markdown, comments) ├─ Validate (block DROP/DELETE/UPDATE) ├─ Execute in DuckDB └─ Return DataFrame ↓ [Chart/Response Generation] └─ Use DataFrame for visualization or LLM context

Platform type (mobile vs desktop) comes from the Allure "Project" parameter, NOT text-matching on test names:

  • GoogleChrome → desktop
  • GoogleChromeiPhoneX → mobile
  • GoogleChromeiPad → mobile

  • Graph-based: Knowledge graph edge traversal for related concepts

Impact: More accurate context retrieval → better responses, faster queries

2. Failure Root Cause Analysis

Analyze failure patterns across builds to detect:

  • Repeated failure signatures (similar errors across tests)
  • Flaky test detection (fails occasionally)
  • Correlation between failures and infrastructure changes
  • Regression patterns (new vs existing failures)

Implementation: LLM-powered pattern extraction + knowledge graph storage

3. Proactive Test Health Monitoring

Generate automated insights without waiting for user queries:

  • Daily/weekly health summaries (pass rate trends, slowest tests)
  • Risk alerts (high-impact modules failing)
  • Anomaly detection (unusual test duration, failure clustering)

Implementation: Scheduled jobs with LLM-powered insight generation

5. Multi-Modal Intelligence

Combine multiple data sources for richer insights:

Code Smells & Refactoring Candidates

1. Hardcoded Prompt Templates in Code

Location: services/prompts.py

All prompt templates are embedded as string constants. While this works, it makes AB testing and versioning difficult.

Suggestion: Move prompts to database or structured config; add version tracking and A/B test capability.

2. Global State in services/state.py

Location: services/state.py

Application state (current_ingestion_id, lance_db, duck_conn) stored in module-level globals. Makes testing harder, potential race conditions in async context.

Suggestion: Use FastAPI dependency injection; pass state as context parameter to handlers.

3. Missing Error Handling in Ingestion

Location: universal_ingester/ingester.py

Limited try-catch in connector fetch operations. If one source fails, entire ingestion fails silently.

Suggestion: Implement partial ingestion success; log errors per source; return detailed ingestion report with partial data warning.

4. Monolithic handlers.py

Location: services/handlers.py

Chat and chart logic mixed together; 300+ lines of interdependent functions. Hard to test, high cyclomatic complexity.

Suggestion: Split into chat_handler.py and chart_handler.py; extract validation logic to separate module.

5. Frontend Type Safety Gaps

Location: frontend/lib/api.ts, component files

Many any types used in API responses; potential null reference errors. Props not always typed in components.

Suggestion: Add strict TypeScript; use discriminated unions for API response types; run npm run lint pre-commit.

6. SQL Generation Without Type Safety

Location: services/handlers.py

LLM generates SQL strings that are string-concatenated into queries. While validated, no compile-time type checking.

Suggestion: Consider SQL query builder (sqlglot) to construct queries programmatically; validate AST before execution.

7. Inconsistent Error Response Format

Location: Multiple endpoints in main.py

Some endpoints return { "error": "..." }, others { "detail": "..." }, some throw HTTPException. Inconsistent client error handling.

Suggestion: Create standardized error response schema; use exception handler middleware; document error codes.

8. Missing Logging & Observability

Location: Backend services (sparse logging)

Limited structured logging; no request IDs for tracing; token usage tracked but not exposed as metrics.

Suggestion: Add request/response logging middleware; implement structured logging (JSON format); expose Prometheus metrics.

9. No Input Validation on Frontend

Location: Form inputs across components

User input accepted without client-side validation (length, format, special chars). Relies on backend validation.

Suggestion: Add zod or yup for schema validation; provide immediate user feedback.

10. Coupling Between Auth and Workspace

Location: services/auth.py, header handling

Workspace ID mixed into auth token and headers. Makes it unclear which is source of truth for tenant context.

Suggestion: Define clear tenant isolation boundary; make workspace part of explicit authorization context (not magic header).

Security Assessment

Current Security Controls

✓ Strengths

  • JWT Authentication: Bearer tokens with 24-hour expiry; HS256 HMAC
  • Password Security: bcrypt hashing with configurable rounds (default 12)
  • SQL Injection Prevention: LLM-generated SQL validated against disallowed keywords
  • CORS Protection: Configurable origin allowlist (not wildcard)
  • Environment Secrets: Sensitive values loaded from .env (not hardcoded)
  • Role-Based Access: Admin/CTO vs QA Engineer roles restrict cross-user access

Security Issues & Recommendations

🔴 Critical: Hardcoded Credentials in config.json

Location: config.json contains TiDB connection string with plaintext password

Risk: Database credentials exposed if repo is leaked or in shared environments

Fix:

  • Never commit credentials; use environment variables only
  • Example: DB_CONNECTION_STRING=mysql+pymysql://user:pass@host/db in .env
  • Add config*.json to .gitignore
  • Use secrets management (HashiCorp Vault, AWS Secrets Manager) in production

🔴 Critical: Gemini API Key in .env (Visible)

Location: .env file contains LLM_API_KEY (checked into git history)

Risk: API key compromised = unauthorized API usage, cost explosion, data leakage

Fix:

  • Never commit .env to git; add to .gitignore
  • Use local .env.local for development (not in git)
  • Rotate API keys immediately if exposed
  • Use short-lived credentials (refresh tokens)
  • Implement API rate limiting and quota alerts

🔴 High: JWT Secret in .env (Weak)

Location: .env contains SECRET_KEY

Risk: If exposed, attacker can forge JWTs and impersonate any user

Fix:

  • Ensure SECRET_KEY ≥32 characters (config.py validates minimum length)
  • Use cryptographically secure random value: python -c "import secrets; print(secrets.token_urlsafe(32))"
  • Rotate SECRET_KEY periodically (invalidates all existing tokens)
  • Store in secure secrets manager, not .env files

🔴 High: No HTTPS Enforcement

Location: Frontend/backend assume HTTP in development

Risk: Tokens, credentials, and data transmitted in plaintext over network

Fix:

  • Deploy backend with HTTPS only (use Let's Encrypt for certs)
  • Set Secure and HttpOnly flags on JWT cookies (if using cookies instead of localStorage)
  • Add HSTS header (Strict-Transport-Security) to force HTTPS
  • Use TLS 1.3 minimum

⚠️ Medium: Token Stored in localStorage

Location: frontend/lib/api.ts

Risk: Vulnerable to XSS attacks; attacker can steal token and impersonate user

Mitigation:

  • Implement Content Security Policy (CSP) to prevent inline scripts
  • Consider moving to httpOnly cookies (harder to steal via XSS)
  • Add token expiry refresh mechanism (shorter-lived access tokens, long-lived refresh tokens)

⚠️ Medium: SQL Query Validation (Partial)

Location: services/data_loader.py

Risk: Regex-based keyword blocking can be bypassed (e.g., DROP with spaces, backticks)

Fix:

  • Use SQL parser (sqlglot) to validate query structure
  • Only allow SELECT statements; parse and validate whitelist of allowed tables
  • Test against known SQL injection patterns

⚠️ Medium: No Rate Limiting

Location: FastAPI routes (no middleware)

Risk: Brute force attacks, DoS, LLM token quota exhaustion

Fix:

  • Add rate limiting middleware (slowapi for FastAPI)
  • Implement per-user and per-IP limits
  • Track LLM token spend; set per-user/per-workspace quotas
  • Alert on unusual activity (spike in requests, quota overage)

⚠️ Medium: No Input Sanitization on Chat Prompts

Location: services/handlers.py chat handler

Risk: Prompt injection attacks (adversarial input to LLM)

Fix:

  • Validate prompt length (reject extremely long inputs)
  • Implement prompt injection detection (check for "ignore previous instructions")
  • Add user feedback loop to flag malicious prompts
  • Log and monitor suspicious patterns

⚠️ Medium: Workspace Isolation Not Enforced

Location: Data loading and querying

Risk: If x-workspace-id header is spoofed, user could access other workspace data

Fix:

  • Extract workspace_id from JWT token (not header)
  • Validate all queries are scoped to current user's workspace
  • Add integration tests for cross-workspace access denial

⚠️ Low: CORS Allowlist Default

Current: Defaults to http://localhost:3000 (dev-only)

Risk: Production may accidentally use dev allowlist

Fix:

  • Fail startup if CORS_ALLOWED_ORIGINS not explicitly set (no default for prod)
  • Document the env variable requirement

Identified Bottlenecks

1. Initial Ingestion Load Time (Critical)

Bottleneck: First chat/chart request on a new ingestion triggers:

  • LanceDB load from disk (I/O bound)
  • DuckDB table registration
  • Aggregate table computation (module_metrics, project_metrics)

Impact: 5-30 second delay on first request

Solution:

  • Pre-compute aggregates during ingestion (not lazy)
  • Implement background job to warm up database on startup
  • Show loading indicator to user with estimated time
  • Cache metadata (# tests, # modules) after first load

2. Large Ingestion Dataset Performance (High)

Bottleneck: Ingestions with 100K+ tests can be slow to:

  • Generate embeddings (sentence-transformers inference)
  • Compute aggregates (full table scans)
  • Store in LanceDB (write throughput limited)

Impact: Ingestion takes 10+ minutes for large datasets

Solution:

  • Batch embeddings (process 100 records at a time)
  • Parallelize ingestion across CPU cores (use ProcessPoolExecutor)
  • Streaming writes to LanceDB (don't load entire dataset into memory)
  • Show progress bar to user during ingestion

3. LLM API Latency (High)

Bottleneck: Chat/chart requests block on LLM API calls (1-10 seconds per call)

Impact: User waits for response; poor UX for poor internet

Solution:

  • Implement streaming responses (stream token generation to client)
  • Add response caching for repeated queries
  • Use faster model for simple queries (fallback to expensive model for complex)
  • Implement timeout with graceful degradation (return cached result if LLM times out)

4. Knowledge Graph Traversal (Medium)

Bottleneck: knowledge_graph_edges table can grow unbounded; queries slow with many edges

Impact: Context retrieval takes 100ms+ for large workspaces

Solution:

  • Implement edge pruning (keep top N edges by weight)
  • Add index on edge sources/targets
  • Limit traversal depth (2-3 hops max)
  • Cache related concepts for popular queries

5. Frontend Rendering Performance (Medium)

Bottleneck: ChartGallery with 50+ charts can lag when rendering/updating

Impact: Scroll jank, slow interactions

Solution:

  • Virtualize chart list (render only visible charts)
  • Use React.memo for chart components
  • Lazy load chart images (use IntersectionObserver)
  • Move animations to CSS (not JS animation frames)

6. SQL Query Complexity (Medium)

Bottleneck: LLM sometimes generates inefficient SQL (nested queries, full table scans)

Impact: Query takes 5+ seconds instead of <100ms

Solution:

  • Add SQL optimization pass (rewrite to use indexes)
  • Profile slow queries; provide feedback to LLM prompt
  • Implement query timeout (5s max); return approximation if exceeded
  • Suggest index creation for frequent column filters
