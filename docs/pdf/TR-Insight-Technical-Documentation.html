1. Executive Summary

TR-Insight is a self-hosted, full-stack AI analytics platform for software test results. It ingests test output from any existing source — Allure JSON reports, spreadsheets/files, relational databases, generic APIs, or a live Playwright/Cypress test run — normalizes it into a common analytical schema, and exposes it through a role-aware web dashboard, a conversational AI interface, and a deterministic chart-generation engine.

It is the test-reporting member of Testrig Technologies' TR-TestIntelligence suite:

FrameworkPurpose
TR-ForgeAI-assisted test case generation
TR-AutomatePlaywright test automation with AI assistance
TR-InsightTest reporting and analytics dashboard (subject of this document)

The architecture separates concerns cleanly: a Next.js frontend, a FastAPI backend, a file-based dual-database storage layer (LanceDB for vector/semantic retrieval, DuckDB for SQL analytics), a pluggable LLM provider abstraction, and an independent live-execution streaming subsystem. There is no external database server or managed service dependency — the entire system runs as one or two containers on a single host, with all state on local disk.

Design principle: the LLM is used only for natural-language understanding and SQL generation — never for producing chart code directly. Chart rendering is deterministic (parsed intent → constrained SQL → validated figure), which makes visual output repeatable, auditable, and immune to LLM hallucination in the rendering path.

6.2 Storage layout

PathDefaultContents
DATA_DIR./dataEvery ingestion (ingestion_*/: LanceDB vectors + DuckDB tables + summary.json), finalized live runs (run_*/), live_runs.db (in-progress only), token_usage_store.json
STATE_DIR./stateusers.db, config2.json, auto-generated secrets (secret_key, bootstrap_admin_password, live_ingest_api_key)

Everything is a bind mount. No state lives inside a container — docker compose down, rebuilds, and image deletion never destroy data. Backup is simply copying DATA_DIR and STATE_DIR (e.g., nightly rsync/tar to off-host storage); there is no database server to dump.

6.3 Multi-table schema fallback

A historical schema migration renamed flattened_tests to structured_test_results. _get_test_results_table() auto-detects and queries try the new name first, falling back to the old one — so older ingested datasets keep working without re-ingestion.

6.4 Multi-ingestion support

Each ingestion is a fully independent, timestamped dataset. The frontend fetches the list via GET /ingestions; the x-ingestion-id header selects which dataset a given API call queries. DuckDB locking is per-ingestion (state.duck_lock), so concurrent queries against different ingestions no longer block each other.

7. Authentication, Authorization & Multi-Tenancy

7.1 Credentials & bootstrap

  • JWT + bcrypt (python-jose for tokens, bcrypt for password hashing). User store: SQLite by default (AUTH_BACKEND=db), or in-memory.
  • Zero-config first run — a bootstrap admin (BOOTSTRAP_ADMIN_USERNAME, default admin) is created only while the user table is empty. If BOOTSTRAP_ADMIN_PASSWORD is unset, one is auto-generated into state/bootstrap_admin_password and logged once at startup.
  • That bootstrap account carries must_change_password=true; a middleware blocks every route except /auth/me, /auth/permissions, and the account-change endpoints until it is cleared — the default password is a one-time door, never a standing credential.
  • Self-generating secrets — SECRET_KEY (JWT signing) and LIVE_INGEST_API_KEY (live-run ingest key) both auto-generate into state/ on first start if left unset, and are reused thereafter.

7.2 Roles vs. permissions vs. personas — three distinct systems

SystemGovernsValues
Account role (permissions.py)What a logged-in user is allowed to doadmin, cto, qa-manager, sdet
WorkspaceWhich builds a user can seeOne per team; non-admins see only their own, admins see all
AI persona (x-role header, roles/*.md)How the AI phrases an answer, independent of what data is visiblee.g. cto.md, qa-manager.md, sdet.md

admin/cto are wildcard-everything. qa-manager and sdet get read/ingest access scoped to their own workspace. Enforcement is server-side — on GET /ingestions, every endpoint accepting x-ingestion-id, and DELETE /ingestions/{id} — not merely a client-side filter.

7.3 Account lifecycle

  1. Bootstrap admin — from .env, applied only while the database is empty.
  2. Self-service registration — /register creates a pending account with no login and no workspace until an admin approves it.
  3. Admin-created — created directly on Users → New user, already active.

7.4 Token quotas & audit

users.token_limit (0 = unlimited) is enforced in main._enforce_token_quota() before any LLM call, checked against a lifetime, account-wide total in token_usage_store. Every login, registration, user/role/settings edit, credential change, and build deletion is written to an append-only audit log (audit_log.py, exposed at GET /admin/audit).

8. LLM Integration Layer

llm_client.py abstracts over any provider litellm supports — not a hardcoded list. Configuration resolves per field with a strict precedence:

env variable > database (Admin → Settings) > built-in default

A field pinned in .env is locked (shown as "locked by env" in the admin UI) and cannot be overridden live; otherwise an admin can set or change provider/model/key/base-URL at runtime from Admin → Settings, including a real one-shot connectivity test — no restart required. LLMClient re-reads settings on every call rather than caching them at construction time.

9. AI Chart Generation Pipeline

Charts are built deterministically; the LLM's only job in this pipeline is writing SQL.

prompt │ ▼ chart_spec.parse() intent extraction (regex, no LLM): form, measure, │ dimension, breakdown, top-N, sort direction, filters ▼ CHART_SQL_PROMPT LLM writes SQL, constrained by the parsed intent │ (handlers._spec_sql_directives()) ▼ execute + repair loop fallback map, then one LLM repair attempt fed the │ actual DB error ▼ chart_spec.reconcile() can the returned data actually support the │ requested form? downgrade if not (e.g. a │ 400-slice pie, a 2-point "trend", a scatter │ with only one measure) ▼ chart_builder.build_figure()

9.1 Supported chart forms (17)

bar · stacked_bar · horizontal_bar · line · area · pie · donut · scatter · bubble · heatmap · treemap · sunburst · funnel · histogram · box · gauge · radar · platform_comparison

9.2 Colour theming

  • Colour is assigned by job, never by rank: categorical hues in a fixed slot order; a reserved status palette (good/warning/serious/critical) only where colour genuinely encodes state; one hue light→dark for sequential data.
  • The palette is validated for colour-blind separation in both light and dark themes (script: scripts/validate_palette.js).
  • Theming is client-side: the backend emits the light rendering plus both palettes and a per-trace meta.slot marker; frontend/lib/chartTheme.ts remaps colour by slot on theme change, so a series keeps its visual identity across light/dark.

Every figure carries an insight subtitle computed from the drawn data (so it can't drift from what's on screen), a scope note when data was truncated or filtered, and a table-view twin for accessibility/export. There is deliberately no LLM-generated chart-code execution path — the legacy CHART_CODE_PROMPT / detect_chart_type() mechanism was removed.

10. Conversational AI (Chat) Pipeline

  • CHAT_DECISION_PROMPT classifies each question into one of: sql, sql_multi (a labelled list of queries for multi-part questions), vector (semantic/historical retrieval), or answer (direct from context).
  • SQL errors are fed back to the model for one repair attempt (handlers._run_sql_with_repair()) before falling back to a keyword map — the fallback answers a simpler question, so it is the last resort, not the first.
  • handlers._extract_json_object() performs a balanced-brace scan so nested decision objects parse correctly (a bare regex could not).
  • Dataset-wide facts (sums, extremes, distributions) are pre-computed over all rows and injected into the prompt, since only the first 50 rows are ever sent to the model directly — this keeps aggregate answers accurate without shipping the full dataset to the LLM.
  • Requests carry context headers: which ingestion, which AI persona (x-role), which project (x-project).

11. Live Test Execution Subsystem

Streams a test run to /runs/live while it is still executing, then folds it into normal history once finished. Implemented by services/live_exec/ (server side) and the sentinel-qa-reporter npm package (client side).

11.1 Design principles

  • Framework-agnostic by contract — four plain HTTP calls: POST /live/runs, POST /live/runs/{id}/events, an optional attachment upload, and PATCH /live/runs/{id}. framework is free text.
  • One client package, two adapters — a framework-neutral src/core/ (HTTP client, CI detection, config resolution, redaction) plus src/playwright/ and src/cypress/ adapters exposed as subpath exports. The Cypress adapter splits into a Node half and a browser half bridged over cy.task; the browser half stays inert unless the Node half enables it, so an unconfigured repo never invokes the task and reporting cannot break a test run.
  • Never fails a run — every request has a deadline; the event queue has a ceiling and sheds log lines before test results under pressure; finish() is idempotent; the worst possible outcome is a single console warning.
  • withSentinel(config) (Playwright helper) injects --remote-debugging-port into both the top-level and every Chromium project's launchOptions.args — required because Playwright replaces rather than merges project-level launchOptions, so a naive top-level flag would silently never reach the browser in any repo whose projects define their own args.

11.2 Hot layer, sharding, and finalization

  • Hot layer — SQLite WAL (store.py) holds in-progress runs only; a finalize job promotes a completed run into LanceDB and deletes the hot rows. Abandoned runs are swept by store.reap_stale_runs.
  • Sharding — several runner processes can share a SENTINEL_RUN_KEY (sent as external_id) to attach to one logical run, summing total_tests/worker_count and tracking active_runners. update_run_status only lets the last shard finalize the run; an early shard failure is parked in pending_status so viewers keep seeing "running" until the whole run is actually done.
  • Push — in-process pub/sub (bus.py) fanned out over Server-Sent Events. A multi-replica deployment needs REDIS_URL for this to work across instances.

11.3 Distribution & key management

  • Docker images build the reporter's tarball into a reporter-builder stage and serve it unauthenticated at GET /live/package — intentional, since it is public client code and npm install carries no JWT. A team pulling the image gets a client that matches their server by construction, with no npm registry step.
  • GET /live/connection-info (admin-only) returns this install's real ingest key, a request-derived base URL, and the exact install command, rendered as copy-paste snippets under Live Runs → Connect a repo.
  • POST /live/connection-info/rotate reissues the key without a restart, and returns 409 if the key is pinned via environment variable.

Documented VM starting point: t3.large (2 vCPU, 8 GB RAM) — sized for the backend's in-memory embedding model; t3.medium is enough to evaluate. Container log files are capped (10 MB × 3) on every service.

12.3 Scaling

  • Single instance is the default and needs nothing extra — WEB_CONCURRENCY=1 by design, since services/state.py holds the active ingestion as mutable process state.
  • Multiple backend replicas behind a load balancer require REDIS_URL (docker compose --profile multi-instance up) so the live-run SSE bus and live-frame cache work across instances.
  • No database server to scale separately — LanceDB and DuckDB are both file-based under DATA_DIR.

14. Security Model

  • Self-hosted by design — the entire system, including all test data and defect detail, runs inside the customer's own environment; nothing is sent to a third-party SaaS backend for storage.
  • Secrets never ship with defaults — SECRET_KEY, LIVE_INGEST_API_KEY, and the bootstrap admin password all auto-generate into state/ and are logged once at startup if not explicitly set; there is no fixed factory credential.
  • Forced credential rotation on first use — the bootstrap admin account is locked to account-settings-only routes until its password is changed.
  • Password hashing — bcrypt, configurable cost factor (BCRYPT_ROUNDS, default 12, range 10–16); minimum password length enforced (MIN_PASSWORD_LENGTH, default 8).
  • Workspace isolation enforced server-side on every data-bearing endpoint, not just hidden in the UI.
  • Token-spend quotas checked before every LLM call, closing the "runaway AI bill" risk at the request layer, not just via a dashboard after the fact.
  • Append-only audit trail of all security-relevant actions, exposed to admins/CTOs via GET /admin/audit.
  • CORS allow-listing (CORS_ALLOWED_ORIGINS) — no wildcard origin in a real deployment.
  • Live-ingest key gates the unauthenticated-by-design /live/package download boundary — the download itself is public client code, but reporting a run in requires the per-install key.
Note for security review: because there is no external database server and no data leaves the host, the security review surface for a self-hosted deployment is limited to the host itself, its Docker configuration, TLS termination, and the chosen LLM provider's own data-handling terms (relevant only for the prompt/response traffic actually sent to it — see §8).
